# Риски и как проект их снижает

Прочитайте один раз перед запуском.

## 1. Нарушение ToS Telegram

Автоматизация действий пользовательского аккаунта запрещена правилами Telegram
независимо от того, разрешил ли админ чата публикации. Это остаётся так даже при
полностью «белом» использовании.

**Последствия:** ограничение отправки сообщений незнакомым чатам (`PeerFlood`),
спам-блок, в тяжёлых случаях — блокировка аккаунта. Блокируется номер телефона,
то есть теряется и личная переписка.

**Что делает проект:** соблюдает `FloodWait` буквально, держит консервативные
лимиты, не публикует чаще правил чата, автоматически встаёт на паузу при первых
признаках ограничений.

**Что можете сделать вы:**
- Начать с малого — 5–10 чатов, 1 пост в сутки, и понаблюдать неделю.
- Не использовать основной номер, если потеря переписки критична.
- Держать аккаунт «живым»: он не должен состоять только из объявлений.

## 2. Бан админами чата

Даже там, где объявления разрешены, слишком частые публикации раздражают.

**Что делает проект:** `posts_per_day` и `min_interval_minutes` на каждый чат,
статистика по чатам, отметка `denied` — чтобы больше туда не постить.

**Что можете сделать вы:** ставить частоту ниже разрешённого максимума и
отслеживать реакцию.

## 3. Компрометация сессии

Строка сессии Telethon = полный доступ к аккаунту.

**Что делает проект:** сессия шифруется (Fernet), ключ хранится отдельным
файлом, в git ничего из этого не попадает, секреты не пишутся в логи.

**Что можете сделать вы:** ограничить доступ к VPS, бэкапить ключ отдельно от
базы. См. `docs/SECURITY.md`.

## 4. Потеря контроля над рассылкой

**Что делает проект:** режим `DRY_RUN` (прогон без реальной отправки), кнопка
паузы в панели, все публикации планируются заранее и видны в панели до отправки.

## Рекомендуемый первый запуск

1. `DRY_RUN=true`, импорт чатов, разметка разрешений.
2. Сутки посмотреть, что планировщик собирается делать.
3. Включить реальную отправку на 3–5 чатах.
4. Расширять постепенно.
